ORDER PROCESSING · SEQUENCE

Acceptance first. Fulfilment later.

Authorization gates every order. An allowed request stores the order and queues work before returning 202; fulfilment and its final state happen afterward.

Read time downward. Dashed arrows are returns; open solid arrows are asynchronous messages. On a narrow screen, scroll the diagram or read the flow below.

The flow in words

  1. The browser submits an order to the API.
  2. The API checks authorization. If denied, it returns 403 immediately and the path ends.
  3. If allowed, the API stores an order in the database, publishes a job to the queue, then returns 202.
  4. A worker later receives the queued job and calls the fulfilment service.
  5. Success leads to an order marked complete. Failure leads to a recorded failed state.

Known limits

Retry policy is unknown. The diagram does not introduce a retry loop, retry count, backoff or dead-letter path.

The worker's state updates are shown as self-actions. The brief does not specify where the worker records state, so no storage target is added.

Fulfilment outcomes appear as responses for readability. Storage/publish failures, queue delivery guarantees, timing durations and message fields are unspecified.

202 describes the API response before later processing; it does not mean fulfilment succeeded.
